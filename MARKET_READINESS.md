# Market readiness review

## Assessment

This repository is a credible prototype with a useful deterministic policy boundary, but it is not ready to sell as an industrial lead-management system. The existing architecture and UI demonstrate a workflow; they do not yet establish secure multi-company operation, reliable integrations, or production service levels. “Perfect” cannot be verified from source code alone: customer identity systems, CRM/communications credentials, deployment configuration, and operational ownership are not present in this workspace.

## Confirmed gaps

| Area | Current evidence | Required before selling |
|---|---|---|
| Identity and authorization | API routes validate HTTPS-hosted OIDC RS256 bearer tokens, required `exp`/`iat`/`sub`, resource audience (or `client_id` only when `aud` is absent), required scope, tenant claim, and now require operator/admin roles for customer-data reads as well as existing writes. The browser has PKCE sign-in and memory-only token handling; there is no refresh-token lifecycle, and the flow has not been validated against a real provider. | Validate provider discovery/CORS/role claims and audience semantics, test sign-in/out and key rotation, and complete security review. |
| Company separation | Each API deployment validates one tenant claim; lead, follow-up, and audit items now carry that tenant, and list/detail paths enforce it. The runtime still serves only one tenant per deployment, so shared SaaS orchestration is not implemented. | Keep isolated stacks per customer for the first release; shared SaaS needs per-request tenant repository context and cross-tenant isolation testing. Backfill existing rows before switching a stack to these indexes. |
| Database reliability | Demo mode can fall back to process memory, which disappears on Lambda recycle. Inbound webhook, manual lead creation, analysis, response approval/edit/rejection, successful rescue, lifecycle status changes, follow-up completion, and company-config updates now atomically write their associated records. State-changing workflows use conditional writes to reject stale updates. SAM enables point-in-time recovery for leads, follow-ups, audit, and config tables. | Keep memory fallback demo-only (now enforced), run restore drills, complete migrations, and establish remaining idempotency and recovery procedures. |
| Scale and query costs | Lead and follow-up pages query tenant-scoped GSIs; audit history queries a tenant-plus-lead GSI and is now cursor-paginated. Pages cap at 100. Single-tenant partition throughput still needs load validation. | Establish capacity/cost targets and load tests; assess write/read hot partitions at expected customer volumes. |
| Deploy security | SAM defaults production mode, uses a configured API origin, scopes Bedrock invocation to the model ARN, requires OIDC and tenant parameters, scopes DynamoDB operations, and throttles the API stage (default 50 requests/second, burst 100) with a per-deployment worker concurrency cap. Backend Python dependencies are hash-locked for Python 3.12 Linux x86_64, and the frontend has an npm lockfile. WAF policy, customer-specific encryption/key policy, and deployment review remain open. | Add edge protection, maintain the Python and npm lockfiles, define key/secret and encryption policy, separate environments, and complete deployment/security review. |
| Demo controls | Seed/clock endpoints share the API router but return 404 unless both demo mode and a local/test environment are active. | Keep seed/clock routes unreachable in every deployed environment and validate that behavior in staging. |
| Integrations | A signed, tenant-isolated inbound webhook now accepts lead events with replay protection, 30-day idempotency, and an atomic lead/audit/event transaction. No vendor-specific OAuth/CRM sync, bidirectional updates, messaging, or delivery receipts exist. | Pilot the generic connector with an actual source system; then add vendor OAuth/field mapping, consent sync, delivery status, and connector health. |
| Business configuration | Admin changes are role-gated, audited atomically, and validate SLA, deal threshold, business name, locations, JSON shape, and payload size server-side. Secret-like keys are rejected on new updates; existing secret-like values are masked from API responses and preserved if unrelated settings are saved. | Migrate any credentials previously stored in config into Secrets Manager; validate customer-specific rules and define approval/change-control for high-impact updates. |
| Messaging | Approval currently records `SIMULATED_SENT`; it does not deliver a customer message. | Provider adapter, delivery receipts, deduplication, retry/dead-letter handling, and human approval policy. |
| Agent reliability | The browser's analysis flow now creates a durable SQS job and polls a tenant-checked DynamoDB job record. A separate worker retries up to three deliveries, writes terminal failure state, and sends crashed messages to a monitored DLQ. The legacy `/analyze` route remains synchronous for existing API clients. No tenant-specific model policy or evaluation/quality monitoring is evident. | Migrate external clients to the job endpoint, establish model quality evaluation and per-tenant cost/data controls, and validate queue recovery and job-state transitions in AWS staging. |
| Privacy/compliance | New lead-received audit events no longer copy customer names, seed events avoid names, and follow-up status audit events omit free-text notes. Existing historical audit records are not rewritten. A company-admin-only, tenant-scoped export now downloads one lead with all linked follow-ups and paginated audit history; it is no-store and logs the export. Email/phone contact opt-outs now have a durable tenant-scoped suppression registry with transactional safeguards, but existing records must be backfilled before traffic resumes. There is still no contact-wide export, retention/deletion workflow, or documented data processing controls. | Run and verify the opt-out backfill per tenant before cutover; add complete data-subject access/deletion and retention workflows across linked records; define consent, encryption/key policy, access logs, incident process, and jurisdiction-specific review. |
| Operations | SAM sets a 90-day default Lambda log retention and now requires an SNS alarm topic, with API/worker error and throttle alarms plus queue-age/DLQ alarms. The template cannot prove that the topic has verified subscribers or an active on-call owner. Dashboards, SLOs, traces, incident ownership, restore drills, and recovery runbooks are not present. | Configure and verify the production SNS topic and on-call delivery, define dashboards/SLOs and owners, add traces and incident procedures, and run restore drills. |
| Product evidence | README now labels the product a prototype; the current dataset and messaging behavior remain synthetic/simulated. No customer outcomes or supported-service commitments are established. | Define ICP/onboarding/support, prove ROI with pilots and publish honest integration/support boundaries. |
| Release quality gates | No repository CI workflow was present. A pull-request/push workflow now builds the frontend, checks Python syntax, verifies the generated backend lock, and validates the SAM template. It does not run behavioral/security/load tests or deploy automatically. | Require successful CI checks in repository branch protection; add security/dependency scanning, integration tests, deployment review, and staging verification. |

## Changes made in this review

- SAM production defaults disable demo behavior (`DEMO_MODE=false`, `APP_ENV=production`); demo clock and seed routes return 404 in all deployed environments.
- FastAPI CORS now uses configured origins and does not permit credentialed wildcard access.
- SAM defaults demo mode off, accepts an explicit trusted API origin, and narrows Bedrock invocation to the configured foundation model ARN.
- Production repositories now propagate DynamoDB failures instead of pretending writes succeeded in process memory.
- Production lead analysis now returns HTTP 503 when Bedrock is unavailable; heuristic analysis is limited to explicitly enabled demo mode.
- All `/api` routes now require an OIDC RS256 bearer token whose audience and tenant claim match deployment configuration. Unauthenticated local requests remain available only with explicit demo mode.
- OIDC access tokens must carry a configured API scope; OIDC and JWKS endpoints must use HTTPS.
- JWT validation requires expiration, issued-at and subject claims; a token with a different resource `aud` is rejected even if its `client_id` matches the browser app.
- Lead and follow-up writes and company-config changes are role-gated; audit entries now record the authenticated subject for those user actions.
- Lead and follow-up list routes now return at most 100 records per request with filter-bound continuation cursors; the browser loads additional pages on demand.
- Lead, follow-up, and audit repositories now query tenant-scoped GSIs; IDs from another tenant are treated as not found, and writes are conditioned on the configured tenant.
- Added [backend/scripts/backfill_tenant_data.py](backend/scripts/backfill_tenant_data.py) for a read-only-by-default, explicit per-customer legacy data migration.
- Added a signed inbound lead endpoint, Secrets Manager-backed HMAC verification, replay protection, and transactional idempotency; setup and sender protocol are in [INTEGRATIONS.md](INTEGRATIONS.md).
- Webhook idempotency markers now bind new event keys to the signed raw-body digest and return HTTP 409 when a key is reused with different content.
- Added cursor pagination to per-lead audit history and reduced new audit-event PII by omitting customer names and free-text follow-up notes.
- Replaced broad SAM DynamoDB CRUD grants with table/index-scoped permissions for the repository operations actually used by the API and signed webhook.
- Manual lead creation now writes the final lead state (including opt-out detection) and its initial audit event in one DynamoDB transaction.
- Response approval/edit/rejection now atomically update the lead and write all corresponding audit events; stale concurrent edits receive HTTP 409 instead of overwriting the newer lead.
- Successful rescue now atomically changes the lead, inserts its follow-up, and records the audit event; a competing update to that lead causes HTTP 409.
- Analysis now atomically saves the analyzed lead, any recommended follow-up, and its audit event; stale analysis results are rejected with HTTP 409.
- Lifecycle status changes now commit with their audit event, rejecting stale operator updates with HTTP 409.
- Follow-up completion/cancellation/blocking now commits the task and audit event in one DynamoDB transaction; a stale status change returns HTTP 409.
- SAM now enables point-in-time recovery on core data tables, applies bounded Lambda log retention, and defines Lambda error/throttle alarms with an optional SNS notification topic.
- Company business-rule updates now commit with their audit events in one transaction and use conditional writes to reject simultaneous administrator edits with HTTP 409.
- Server-side settings validation now constrains policy inputs and bounds extension JSON to 64 KB with DynamoDB-compatible numeric values; the settings form mirrors the same ranges.
- Database-backed FastAPI handlers now run as synchronous endpoints in FastAPI's worker thread pool; the signed webhook keeps async request-body streaming but moves blocking Secrets Manager and DynamoDB work to the thread pool. This prevents boto3 and Bedrock calls from blocking the ASGI event loop. The legacy `/analyze` endpoint remains request-bound, while the browser uses the durable job flow.
- Bedrock context now excludes customer email/phone, prior message summaries, lead identifiers, and arbitrary business-rule extensions; it includes only the inquiry, display name/source, a prior-interaction count, and selected company context. Agent output now rejects extra workflow fields and caps generated text/list sizes. This reduces unnecessary disclosure but does not replace customer-specific data-processing terms or retention controls.
- Lead analysis now has a durable `POST /api/leads/{lead_id}/analysis-jobs` flow with authenticated status polling, client idempotency keys, request/failure audit events, SQS retry/redrive, a separate least-privilege worker, job TTL, per-deployment concurrency cap, and queue-age/DLQ alarms. The worker records the job ID with the transactional lead update so a redelivered message after a successful write does not repeat the analysis workflow. The older synchronous endpoint is retained for compatibility.
- SAM now defines the API stage explicitly and applies configurable per-method throttling defaults (50 requests per second, burst 100), in addition to the Bedrock worker concurrency cap, to limit request floods and bound AI spend pressure per isolated customer stack.
- Lead, follow-up, audit, and business-configuration read endpoints now require the configured sales-operator or company-admin role, closing the prior gap where any scoped tenant token could read customer records.
- Backend direct dependencies are pinned to the versions present in the checked-in development environment; the unused `strands-agents-tools` package was removed from runtime requirements. Local frontend instructions now use `npm ci` with the checked-in lockfile.
- Backend `requirements.txt` now pins the complete Python 3.12 Linux x86_64 runtime dependency graph with package hashes; `requirements.in` is the direct-dependency source used to regenerate it with uv.
- Added `.github/workflows/quality.yml` to build the frontend, verify the pinned Python dependency graph remains reproducible, check backend syntax, and lint-validate the SAM template on pull requests and pushes to `main`.
- SAM deployments now require an SNS alarm topic and route API/analysis-worker errors and throttles, queue age, and DLQ alarms to it; README documents subscriber verification before deployment.
- Added a tenant-scoped, company-admin-only lead record export covering related follow-ups and every audit page; the API records the export action and returns the JSON as a private, no-store download from the lead detail UI.
- Opt-outs now create durable tenant-scoped email/phone suppression keys. New leads, analysis, response approval, rescue, and lifecycle changes check those keys; state-changing DynamoDB transactions check or write suppression markers atomically to close race windows. Added a dry-run-first backfill script and a tenant migration marker; API/webhook operations fail closed until the marker exists.

## Release gates still open

1. Validate browser sign-in/out, token expiry, provider role claims, and key rotation with the selected identity provider; decide refresh-token/session behavior.
2. Add the new DynamoDB GSIs, run the backfill dry run, apply it per isolated customer stack, and verify item/index counts before routing traffic.
3. Load-test tenant-scoped indexes, hot partitions, and end-to-end pagination, including audit history.
4. Connect and pilot the signed webhook against one actual company source; implement vendor-specific CRM sync and a real messaging provider with consent enforcement.
5. Configure the production alarm topic, add WAF/rate limits and encryption policy, and verify deployment/security/operations controls in a real AWS staging account.
6. Pause intake/outreach/worker processing, backfill existing opted-out contacts, then enable traffic only after the tenant suppression migration marker is present.
7. Run security, integration, load, restore, and agent-quality validation using approved synthetic or customer-authorized data.

The source currently supports none of the claim that company data integrations are complete. Production account configuration and connector credentials would be needed to validate that claim.
